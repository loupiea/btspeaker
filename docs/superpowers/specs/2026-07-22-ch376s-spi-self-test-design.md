# CH376S SPI 通信自检设计

## 目标

在不访问 U 盘和文件系统的前提下，验证 ESP32 能通过硬件 SPI 与板载 CH376S 通信，并读取芯片固件版本字节。成功标准是 `CHECK_EXIST` 返回正确的按位取反值，随后 `GET_IC_VER` 返回可记录的原始版本字节。

## 范围

本阶段只实现 CH376S 的 SPI 总线初始化、接口自检和版本读取。暂不初始化 USB Host 模式，不检测 U 盘，不挂载文件系统，也不恢复 TF 卡测试。

## 硬件接口

CH376S 与 TF 卡共用 ESP32 VSPI 信号，但使用独立片选：

| 信号 | ESP32 GPIO | 说明 |
|---|---:|---|
| SCLK | GPIO18 | 硬件 SPI 时钟 |
| MISO | GPIO19 | CH376S SDO 到 ESP32 |
| MOSI | GPIO23 | ESP32 到 CH376S SDI |
| CH376S CS | GPIO15 | 软件手动控制，低电平有效 |
| TF CS | GPIO5 | 本测试全程保持高电平 |

CH376S INT 未连接，本阶段不依赖中断。

## 软件结构

在 BSP 中新增独立组件文件：

- `software/bsp/include/bsp_ch376.h`：公开初始化、自检、读取版本和释放接口。
- `software/bsp/src/bsp_ch376.c`：封装 SPI 设备、手动片选和 CH376S 命令时序。

`main/main.c` 只负责调用 BSP，并根据返回值打印最终测试结果。CH376S 命令常量保留在实现文件中，避免业务代码依赖芯片协议细节。

## SPI 配置与时序

- 使用 ESP-IDF SPI Master 驱动和 `SPI3_HOST`。
- 使用 SPI Mode 0，MSB first，初始频率 1 MHz。
- SPI 设备不配置自动片选，由 GPIO15 手动拉低和拉高。
- 每条命令开始前拉低 GPIO15，结束后拉高 GPIO15。
- 命令字节发送完成后等待至少 2 微秒，再发送或读取后续数据，覆盖数据手册约 1.5 微秒的接口处理时间。
- 初始化前将 GPIO5 和 GPIO15 都拉高，防止 TF 卡与 CH376S 同时选中。
- BSP 拥有本阶段的 SPI 总线；初始化失败或测试结束时提供明确的释放路径。

## 测试流程

1. 初始化 GPIO5、GPIO15 和 SPI3 总线。
2. 执行 `CHECK_EXIST`：发送命令 `0x06` 和测试字节 `0x65`。
3. 验证返回字节等于 `0x9A`，即 `~0x65` 的低八位。
4. 只有通信自检通过后才执行 `GET_IC_VER` 命令 `0x01`。
5. 读取并记录原始版本字节，不对未知版本建立过严的白名单。
6. 主程序进入低频空闲循环，不重复高速刷日志。

## 日志与错误处理

成功日志应包含：

```text
CH376S SPI communication OK: 0x65 -> 0x9A
CH376S version raw: 0xNN
```

失败时记录 ESP-IDF 错误名以及实际返回字节：

- `0xFF`：常见于 MISO 被上拉、芯片未选中或芯片没有输出。
- `0x00`：常见于 MISO 被拉低、短路或芯片异常。
- 其他不匹配值：常见于 SPI 模式、位序、时序或信号完整性问题。

上述解释仅用于定位方向；是否为根因仍以实测信号和连接检查为准。

## 验证

- 工程必须在 ESP-IDF 5.4 下完整编译通过。
- 烧录后必须先看到 `CHECK_EXIST` 的 `0x9A`，才能判定 SPI 通信正常。
- 版本号日志本身不能替代 `CHECK_EXIST`，因为单个偶然字节不足以证明双向通信可靠。
- 本阶段不以 U 盘能否识别作为验收条件。
